\subsection{Methodology}

All timings are the \textbf{median of 5 timed runs} preceded by one warmup
run, measured with warm OS page caches.
Our encoder processes individual string columns; DuckDB encodes the complete
file at once. Consequently, raw file sizes reported for DuckDB include all
columns (including numeric fields), whereas raw sizes for our system cover
only the tested string columns. Random access is not natively supported
as a point-query primitive in DuckDB over CSV/Parquet and is therefore
reported for our system only.

\section{Discussion}
% =============================================================================

\paragraph{Compression ratio.}
Adaptive compression excels on low-cardinality repeated columns:
\texttt{views\_stats} col.\,4 (project ID, essentially a foreign key
with many duplicates) achieves 45.79$\times$, while DuckDB/Zstd reaches
24.49$\times$ on the same file. On high-cardinality near-unique columns
(artifact IDs, free-text titles, display names), differential encoding
offers no benefit and expansion occurs (0.88--0.95$\times$); the encoder
correctly falls back to 100\% local pages in these cases. DuckDB/Parquet
with Zstd is generally stronger on high-cardinality text.

\paragraph{Full scan.}
DuckDB on Parquet is faster for full-column materialisation, benefiting
from vectorised execution and columnar projection. For
\texttt{views\_stats}, which has very high differential ratios
(98.7\% diff pages), our decompressor achieves up to 1\,GB/s per column.
DuckDB's 0.9\,ms for four columns on the same dataset is exceptional but
reflects that \texttt{count(col)} in a vectorised engine avoids full
string materialisation.

\paragraph{Filtered scan.}
On low-cardinality columns where page skipping is effective, our filtered
scan is \textbf{competitive with or faster than DuckDB/Parquet}.
For \texttt{views\_stats} col.\,1 (month), we achieve 1.7--2.5\,ms
versus 3.7--3.9\,ms for Parquet/Snappy. On high-cardinality columns with
no zone-map or dict-miss skipping (e.g., access type, boolean), both
systems must examine every page; DuckDB/Parquet is faster there (3--7\,ms
versus 4--11\,ms) due to vectorised filtering. On the high-cardinality
\texttt{artifact\_authors} display name, our dict-miss skipping eliminates
up to 106 of 152 pages, yielding 1.4--3.3\,ms versus
104--108\,ms for DuckDB/Parquet.

\paragraph{Random access.}
Our implementation provides sub-2\,\textmu{}s point queries via the
two-page read scheme. This capability is not directly available in
DuckDB over CSV/Parquet without a full table scan or pre-built index.
